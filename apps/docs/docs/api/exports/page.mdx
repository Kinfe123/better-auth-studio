# Public Exports

The package exposes public imports, declarations, or exported integration helpers.
## What This Is
Public export documentation explains which imports are intended for developers, what each exported helper or type represents, and how those exports connect to the runtime behavior documented elsewhere.
## Why It Matters
Public Exports matters because it is part of how Better Auth Studio turns repository behavior into a usable developer or operator workflow. This page gives readers the mental model first, then uses implementation evidence as supporting context.

- package exports

## Typical Workflow
1. Identify package exports and source declarations that form the public surface.
2. Group exports by the workflow or runtime behavior they support.
3. Document import paths, responsibilities, and related configuration before listing raw symbols.
## Detailed API Contract
Public Exports is a developer contract, not just an exported name. The page explains what the API represents, what problem it solves, what a caller provides, what the package returns or performs, and how it relates to the surrounding runtime.

API pages are most useful when they explain the shape of responsibility. For an adapter, that means the host framework owns routing and the package supplies a handler. For configuration, it means the host app supplies options and the package changes runtime behavior. For utilities, it means the function supports a feature that needs to be understood before the utility is changed.

## Integration Questions
- What does the caller provide?
- What does the package create, mutate, or return?
- Which feature or configuration page explains the user-facing behavior behind this API?
- What needs to be tested after this API changes?

## Success Criteria
- Readers understand the API purpose before looking at source files.
- Readers know whether the API is public integration surface or internal support code.
- Readers know which runtime or feature depends on it.
