# Custom Branding

The product can be customized through branding, metadata, or theme options.
## What This Is
Custom branding explains how the embedded experience can match the host product. It helps developers understand the difference between visual customization and behavior-changing configuration.
## Why It Matters
Custom Branding matters because it is part of how Better Auth Studio turns repository behavior into a usable developer or operator workflow. This page gives readers the mental model first, then uses implementation evidence as supporting context.
## Core Concepts
- brand title
- theme
- logo
- metadata
- visual identity
## Typical Workflow
1. Configure title, theme, and branding metadata.
2. Preview the embedded or standalone UI in the host app.
3. Keep branding changes separate from access, database, or adapter settings.

## Repository Notes
These notes come from the repository README so the page stays grounded in existing project language.

### Configuration Options
| Option                    | Required | Description                                                                                                                                   |
| ------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth`                    | Yes      | Your Better Auth instance                                                                                                                     |
| `basePath`                | Yes      | URL path where studio is mounted                                                                                                              |
| `access.allowEmails`      | No       | Array of admin email addresses                                                                                                                |
| `access.roles`            | No       | Array of allowed user roles                                                                                                                   |
| `access.allowIpAddresses` | No       | IP allowlist for Studio requests. Supports exact IPs and wildcard patterns (example: `192.168.*`)                                             |
| `access.blockIpAddresses` | No       | IP blocklist for Studio requests. Supports exact IPs and wildcard patterns                                                                    |
| `ipAddress`               | No       | IP geolocation for Events/Sessions: `provider` ("ipinfo" \| "ipapi"), `apiToken`, `baseUrl`, optional `endpoint` (ipinfo: "lite" \| "lookup") |
| `lastSeenAt`              | No       | Enable last-seen tracking: `{ enabled: true, columnName?: string }`                                                                           |
| `metadata`                | No       | Custom branding (title, theme)                                                                                                                |
