# Runtime Config

Runtime config defines the options developers pass when wiring the package into an application.
## What This Is
This API reference page explains the configuration shape developers pass into the package, which options are part of the public contract, and which feature pages depend on those settings.
## When To Use This
- Use this when you need the developer-facing contract behind runtime config.
- Start with the purpose and example shape before copying exported names.
- Follow related feature or configuration pages when the API depends on runtime behavior.
## Core Concepts
- configuration type
- runtime options
- validation
- public contract
## Typical Workflow
1. Locate the configuration object in the host application.
2. Set only the options needed for the selected runtime and feature set.
3. Use related feature docs to understand behavior controlled by each option.
## Configuration Entry Points
- `better-auth-studio/config` - Configuration contract or helper export.

## From The README
The README already describes this area in project language. Use these excerpts as the reader-facing baseline before adding more examples.

### ⚙️ Settings & Configuration
- Plugin status - Check which Better Auth plugins are enabled
- Database configuration - View current database adapter and settings
- Social providers - Configure OAuth providers (GitHub, Google, etc.)
- Email settings - Configure email verification and password reset

### Configuration Options
- `auth` (required) - Your Better Auth instance
- `basePath` (required) - URL path where studio is mounted
- `access.allowEmails` (optional) - Array of admin email addresses
- `access.roles` (optional) - Array of allowed user roles
- `access.allowIpAddresses` (optional) - IP allowlist for Studio requests. Supports exact IPs and wildcard patterns (example: 192.168. )
- `access.blockIpAddresses` (optional) - IP blocklist for Studio requests. Supports exact IPs and wildcard patterns
- 3 more settings are described in the README.
